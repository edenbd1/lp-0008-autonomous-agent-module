# Solution: LP-0008 — Autonomous AI Module with Wallet, Storage, and Messaging

**Submitted by:** edenbd1

## Summary

An agent that participates in the Logos stack directly rather than through an API
key: it holds its own shielded LEZ account, and the ceiling on what it may spend
is not a check inside the agent process but **state on chain that the agent's own
program is the only thing permitted to write**.

The core idea is one design decision. An agent runs unattended on a remote node
and holds its own signing key, so any spending rule the agent evaluates can be
evaluated differently by whoever holds the process. So the rule is not evaluated
by the agent at all. Each agent has exactly one policy account, at
`PDA(program, "agent-policy/v1", agent_id)` — the program and the agent, and
nothing else — and the owner, both limits, the period and the running total live
in that account's data, which LEZ rule 6 (`UnauthorizedDataModification`) lets
only this program write. Anchoring one takes two signatures: the agent signs
`claim_agent` to name the account that may bind it, and only that account's
signature is accepted by `create_policy`. `create_policy` is
`#[account(init, …)]`, so the first anchor for an agent is the only anchor for
that agent — a second is not *detected*, it is impossible. `spend` derives the
same address from the *paying* account's id out of the pre-state, so there is no
argument to lie about, and it reads the limits off the account rather than from
the call.

## Approach

### The spending limit is an account, not an `if`

A spending limit enforced inside the agent is enforced by whoever controls the
agent's process — which, for an agent deployed on a remote node with its own key,
is not necessarily the owner. So the limit is moved out of the process entirely.

`create_policy` initialises exactly one account per agent, at
`PDA(program, "agent-policy/v1", agent_id)`. It is `#[account(init, …)]`, and
`init` refuses an account that is not in its default state, so the first anchor
for an agent is the only anchor for that agent. The owner, both limits, the
period and the running total live in that account's data, which LEZ rule 6
permits only this program to write. `spend` derives the same address from the
*paying* account's id, taken from the pre-state the state machine built rather
than from the instruction the agent serialised, so there is no `agent_id`
argument to lie about, and it reads the limits off the account rather than from
the call.

The consequence is checkable from outside with two RPC calls, and the control is
what makes it mean anything: run against an anchored agent, `getAccount` on the
PDA comes back owned by the policy program's own ProgramId; run against an id
nobody anchored, the PDA resolves fine and comes back with a `program_owner` of
all zeros — never initialised, so `init` would still accept it.
`./scripts/use-cases/03-spending-threshold.sh` derives both and prints them side
by side — and it checks the anchored record's owner field against
`artifacts/agents.tsv` as well. `./scripts/verify-deployment.sh` reads every
anchored policy account back off the chain for all three agents and fails unless
each one is owned rather than default, holds a 97-byte v1 record, and carries the
per-transaction limit, per-period limit and period length the manifest claims.

`spend` moves no balance itself, and cannot. LEZ rule 5
(`UnauthorizedBalanceDecrease`) refuses any post-state that decreases the balance
of an account the executing program does not own, and an agent's account is owned
by LEZ's **authenticated transfer** program. So the policy program checks the
anchored envelope and then **chains a call** into the transfer program, which does
own the accounts; the privacy circuit proves both programs and the composition.
`artifacts/programs/authenticated_transfer.bin` is a byte-identical copy of the
chain's own program — not deployed by this repository — committed because the
circuit looks the callee up by ImageID. `demo.sh` checks its ImageID against
`getProgramIds` rather than asserting it.

### What was tried and did not work

The prize asks for this explicitly, and it is the part of this repository with
the most to say. Every item below is a design that shipped and was replaced, not
a hypothetical that was reasoned away.

**Folding the limits into the address.** The original design — and the one this
project recommended at length — put the limits in the *address*:
`PDA(SHA256(owner ‖ agent ‖ per_tx ‖ per_period ‖ period_blocks))`, so that
raising a limit named a different, never-initialised account. It shipped in three
deployments and it does not work. Three successive fixes each added one more
comparison and each time the attack simply moved; the version that mattered
needed no missing comparison at all. An attacker holding a compromised agent's
key does not have to impersonate an owner or borrow a policy — **it is** the
owner: it anchors a *fresh* policy naming the compromised agent and itself, with
`per_tx = per_period = u128::MAX`, and every check passes, because every check is
satisfied. Folding the limits into the address is what made that available: every
`(owner, agent, limits)` triple had an account of its own, all uninitialised, so
"anchor a new policy" was always on the table. One address per agent removes the
choice. `crates/agent-verifier-adversarial` executes the attack against the
deployed binary and asserts the halt code it now stops at, and `demo.sh` replays
it against both programs on the public chain — the superseded one accepted it
([`eedb3caf…0d52e0a7`](https://explorer.testnet.lez.logos.co/transaction/eedb3caf5df94022e6383dec15fa956c7d9c45cd9c3f075ff5a7ff0e0d52e0a7),
block 8869, and the stranger still owns that agent's only policy, for good), and
the identical call to the program deployed today was submitted and is in no
block.

**Anchoring in one signature.** Even with one address per agent, the deployment
before the current one declared only the policy account and a signer it recorded
as the owner; the agent's own account was never declared, never read and never
asked to sign, and `agent_id` was a free `[u8; 32]` argument the body discarded.
So anchoring a policy over somebody else's agent needed **no key at all** — only
the agent's public id, which this repository publishes in `artifacts/agents.tsv`
and inside every signed Agent Card. The fix is the two-signature anchor: the agent
signs `claim_agent` to name the account that may bind it, and only that account's
signature is accepted by `create_policy`. `docs/security-model.md` §2 is the
long form.

**A caller-supplied period total.** `spend` used to take `spent_this_period` as an
argument, which both callers passed as `0`, so the per-period ceiling was advisory
and an agent that always passed zero had a per-transaction limit and no period
limit at all. It now takes `window_start` instead, and does not trust it: the
window must begin on a multiple of `period_blocks`, and the transaction is pinned
to `[window_start, window_start + period_blocks)` by its own block validity range,
so a caller cannot reset its budget by naming a different period.

**An approval that never expired.** An approval account used to be valid in every
block forever, which made it a bearer instrument redeemable the day the agent's
key was stolen. The owner now names the block it dies at, and `spend_approved`
pins the transaction to `[0, expiry)` — an expired approval is not refused, it is
a transaction no block will include.

**"A shielded agent cannot be paid at its shielded account."** This was written up
as an upstream limitation for most of this submission's life. It was wrong. The
`KeyNotFoundError` behind it was a lookup in the *payer's own* key chain, reached
because `spel` built `AccountIdentity::PrivateOwned` for every `Private/`
argument; `spel` is vendored at `vendor/spel` and built here, and now builds
`PrivateForeign { npk, vpk, identifier }` when a recipient is given by keys.
`docs/limitations.md` carries the retraction in full, and the settlement that
closes it is `5942d6cd…` in block 9360.

**"A loaded module cannot have a Delivery node."** A host cannot *pass* a
`std::function` across a plugin boundary — true — which was read as meaning a
module cannot *have* one. It can: the module links `liblogosdelivery` and builds
its ports on the far side of the boundary, and nothing crosses it but
`meta.configure("delivery","on")`. The same mistake was made about payment:
`TaskPort::pay` was unwired with a note saying a settlement needs a wallet and a
sequencer "and this module has neither". The module does not need to *have* a
wallet, it needs to *reach* one.

**Tests that passed while the shipped module did nothing.** `TaskPersistence` had
121 green assertions and **no construction site in the plugin**, so the shipped
module persisted nothing while its tests were green. `meta.skills` was described
in three C++ doc comments as existing while `invoke("meta.skills")` returned *no
skill named 'meta.skills' is registered*. Both are why every criterion below is
asserted against the **packaged artefact** — `module/agent.lgx` loaded through
`QPluginLoader` or through Basecamp's own `liblogos_core` — rather than against a
rebuild or against the source.

**An expectation that went stale where nothing compared it.**
`module/tests/skills_test.cpp` spells out every built-in skill by name, on
purpose, so that removing one from registration turns the suite red *with the
name* rather than with a count. Three skills joined the registry and that list did
not follow, and CI went red — correctly, and expensively: the step runs under
`set -euo pipefail`, so the ten steps after it did not run either. The list is
current again, and it no longer depends on being remembered: `check-docs.py` now
derives the registry from `installBuiltinSkills` and compares all three harness
tables against it, reporting the missing name in seconds rather than in a
compile.

**Two build traps that cost days and are worth naming.** A plugin built against a
Qt whose minor version exceeds the host's makes `logos_core_load_module` return
*success* and join the loaded set; its `logos_host` is then gone and every call
spends twenty seconds timing out. And the plugin referenced
`operator<<(QDataStream&, const LogosResult&)` **without defining it in every
build this repository has ever shipped** — `logos-module-builder` does not compile
`logos_types.cpp`, Mach-O binds lazily and never faulted, and on ELF the module
loads, joins the runtime, hands out a client and then dies on the first call
across the transport, looking exactly like the Qt mismatch. Porting to Linux found
it; nothing else would have. Both are recorded in `docs/basecamp.md`.

### Why Logos, specifically

The payer is a **shielded** account. What a task settlement reveals on a
centralised rail — who paid, for what, how often — is exactly the metadata that
makes an agent marketplace legible to whoever runs it. Here the settlement is a
privacy-preserving transaction signed by the agent's own private account, and the
payee can be shielded too. A payee is named one of two ways and its Agent Card
carries both: by its **public** `paymentAccount`, where the payer stays hidden and
the credit is checkable by anyone with `getAccount` — which is also what makes the
amount, the payee and the timing public — or by `x-logos.shieldedPaymentKeys`, an
`npk`/`vpk` pair that gives nothing away, where both ends are hidden and nobody
but the payee can read the amount. Settlement `5942d6cd…` in block 9360 is the
second form. No centralised payment rail offers the second option at all, and the
first one it offers only to itself.

**A2A leaves two things open on purpose — payment and encrypted transport — and
Logos supplies both natively.** LEZ is the payment layer A2A omits; Logos
Messaging is the transport binding that replaces A2A's HTTP, so two agents
discover each other and negotiate a task with no server in the middle that could
refuse either of them. The relays used in the live runs are third-party public
ones, which is what "no intermediary server" has to mean.

And the property that matters most is the one a centralised stack cannot express
at all: **on a centralised alternative the spending ceiling would be a row in
someone's database rather than an address in a state machine**, and "the agent
cannot exceed its limit" would be a promise instead of a rejection. Here it is
`Program error 6005`, returned by a state machine, with no transaction built.
Logos Delivery gives the owner channel the same property — the owner reaches the
agent because both hold keys, not because a broker is willing to route between
them — and it is why an owner's app on a laptop can answer an agent running
unattended on a remote node with nothing configured in between.

## Design Write-up

The seven topics the submission requirements name, in the order they name them.
Each is answered here in its own right — a reader should be able to follow the
design from this section alone — and each ends by naming the document that
carries the long form. What [Approach](#approach) already argues at length is
cross-referenced rather than restated.

### Module architecture

Everything follows from one constraint: **the agent runs on a machine its owner
does not control.** Anything it decides for itself, whoever takes the process
decides differently. So every decision that matters is pushed either onto the
chain, where the agent cannot rewrite it, or behind a port, where it can be
tested against a hostile fake. What is left in the middle is plumbing.

Read it as three tiers. The chain is the only tier with authority. The ports are
the only tier that touches the outside world. Everything between them is C++
that can be exercised with no node, no network and no key, which is why CI can
check it honestly.

| Piece | Path | Language | Runs where |
|---|---|---|---|
| The anchored policy | `crates/agent-verifier-spel/methods/guest/` | Rust → RISC-V guest | in the zkVM, on the sequencer or inside the privacy circuit |
| The derivations both sides share | `crates/agent-policy-core/` | Rust, `no_std`-capable | compiled twice — into the guest and onto the host |
| The agent module | `module/src/` | C++17 | in the Logos Core process, as a `core` plugin |
| The owner's window | `app/` | C++17, Qt Widgets | in the Logos app, as a `ui` plugin |
| Node drivers | `module/tests/*_drive.c` | C | against a real Delivery or Storage node |
| Operations | `scripts/` | bash, python | the operator's machine |

**The chain tier.** `agent_verifier` is a SPEL program with six instructions, and
five of them exist to make the sixth trustworthy:

| Instruction | Signed by | Accounts | What it is for |
|---|---|---|---|
| `claim_agent` | **agent** | claim (init, PDA of the signer), agent | name the one account that may anchor over this agent |
| `create_policy` | owner | policy (init, PDA), claim (PDA), owner | anchor an envelope, if that claim names you |
| `update_policy` | owner | policy (mut, PDA), owner | re-fix the limits; the way back from a wrong anchor |
| `approve_spend` | owner | approval (init, PDA), policy (PDA), owner | authorise one exact payment, until one exact block |
| `spend` | agent | policy (mut, PDA), agent, recipient | pay inside the envelope, unattended |
| `spend_approved` | agent | policy (PDA), approval (mut, PDA), agent, recipient | pay outside it, on that approval |

That table is the shipped `idl/agent_verifier.idl.json`, which the
`#[lez_program]` macro generates from the same source the guest is built from,
so the CLI and the program cannot describe different ABIs.
`crates/agent-policy-core` is small and load-bearing: it holds the two PDA
prefixes, the two hash derivations, the three record layouts and the spend
decision itself, and it is compiled into the guest *and* onto the host, so a
script that computes a period or a marker seed computes it with the same code
the chain checks — by construction rather than by agreement.

**The module tier.** `AgentModuleImpl` (`module/src/agent_module_plugin.h`) is a
registry rather than a god object. Its whole contract is `configure` once with
the anchored policy address, `start` before any skill call, `stop` before
shutdown, plus `registerSkill`, `skills()` and `invoke()`. Every capability is a
skill behind that one dispatcher, which matters because `invoke()` is the only
thing a `ui` plugin can call across the plugin boundary — it is why the owner's
end of the approval channel is three registered skills rather than a class.

**The port pattern.** No skill links a library. Each takes a struct of
`std::function`s and calls through it — `DeliveryPort`, `StoragePort`,
`SharePort`, `WalletPort`, `ProgramPort`, `SequencerPort`, `OwnerChannelPort`,
the five A2A seams in `module/src/agent_skills.h`, and `HttpTransport` for
inference. This is not indirection for its own sake: it is what lets CI assert
that a skill refuses when the node is down, that `storage.share` blames the
right half of a failed share, and that an owner who never answers is terminal
rather than a quiet fallback — with no node, no network and no model. A real
dependency cannot be made to fail on demand; a fake can.

**A loaded plugin builds its own ports.** A host cannot *pass* a `std::function`
across a Qt Remote Objects boundary, which for most of this project's life was
read as meaning a loaded module could not have a Delivery node. It can: the
module links `liblogosdelivery` and constructs its own `DeliveryPort` and
`OwnerChannelPort` on the far side of the boundary
(`module/src/delivery_runtime.cpp`), and nothing crosses but the two strings of
`meta.configure("delivery","on")`.

**Pending state across a restart.** `TaskStore` holds the A2A lifecycle in
memory; `TaskPersistence` (`module/src/task_persistence.h`) renders it to one
file atomically — temp file, flush, rename, flush the parent — under the host's
`instancePersistencePath()`, `start()` recovers from it, and `invoke()`
checkpoints whenever the store moved. The load-bearing decision is that a
snapshot which cannot be read **refuses the start**, because coming up with an
empty task list on top of an unreadable one is how a paid task gets paid twice.
`meta.status` carries a `durability` block naming the file and the recovery
outcome, so "this agent writes nothing down" and "this agent had nothing to
write" are distinguishable from outside.

**Shipped shape.** `module/agent.lgx` (`type: core`) and `app/agent-ui.lgx`
(`type: ui`), each carrying `darwin-arm64`, `linux-amd64` and `linux-arm64`,
plus a pre-built headless harness per variant under `module/harness/`.

Long form: [`docs/architecture.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/architecture.md)
— the same map as a diagram, the full port and skill-catalogue tables, the
settlement sequence through the privacy circuit, the build and deployment
topology, and a reading order for the rest.

### Skill interface design

One class, three methods, one header —
[`module/src/agent_module_interface.h`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/module/src/agent_module_interface.h):

```cpp
class ISkill {
public:
    virtual ~ISkill() = default;
    virtual std::string name() const = 0;            // stable id, e.g. storage.upload
    virtual std::string parameterSchema() const = 0; // JSON Schema, as a JSON object
    virtual std::string invoke(const std::string &paramsJson) = 0;
};
```

It is the only header a skill needs: not the plugin header, not the Logos SDK,
not Qt, and not a JSON library. Everything crossing the boundary is a
`std::string`, which is a deliberate narrowing — a skill and the module need not
agree on a JSON library or link one at all, and a skill may be compiled by a
different toolchain revision than the module was.

**The interface is defensive because third-party code is the whole point.** All
three methods are called inside a `try`/`catch`, so a skill that throws costs
its own entry and nothing else. None is called while the module holds its own
lock, so a skill may call `skills()`, `invoke()` or `registerSkill()` back from
inside any of them without deadlocking a non-recursive mutex. `name()` is called
**once**, at registration, and the registered name is published from then on — a
name that changed between calls would advertise a skill `invoke()` cannot
dispatch. A `parameterSchema()` that throws, or does not parse as a JSON object,
becomes an error entry in the Agent Card and leaves the other skills alone; that
schema used to be spliced in as raw text, where one malformed schema broke
discovery for every other skill too. An `invoke()` answer that is not JSON is
refused rather than passed on.

**Registration has three rules, all enforced rather than documented.** It must
happen before `start()`, because `skills()` refuses until then and an empty
array is indistinguishable from an agent that genuinely has none. A name is
claimed once — `registerSkill` refuses a duplicate rather than overwriting it,
so one library cannot silently shadow another's `wallet.send`. And a third party
*wins* a contested name: if it registers `wallet.send` first, the built-in is
skipped, the failure is reported naming it, and the other twenty-seven are
registered, so the card can never advertise something `invoke()` will not
dispatch.

**For a skill shipped as a separate binary** the convention is two C symbols —
`logos_agent_skill_abi_version()`, returning 1, and
`logos_agent_skill_create()`. The version is checked *before* `create` is
called, so a library built against a later generation of the interface is a
named refusal rather than a jump into a vtable whose layout moved; the raw
pointer lets the host choose ownership, and the host must not `dlclose` the
library while the module still holds the skill.

**The Agent Card is generated from the registry**, and `meta.skills` reads the
same registry `agent.card` does — so a skill that is registered is advertised,
one that is not is not, and the catalogue and the card cannot become two answers
to one question. The module registers **28** skills: the prize's twenty-one,
plus `agent.evaluate_task` for the pluggable-inference seam, plus
`messaging.receive`, `agent.update` and `agent.poll` without which the A2A
lifecycle only runs in one direction, plus `owner.watch`, `owner.pending` and
`owner.answer`, which are the **owner's** app's skills rather than the agent's.

**The boundary this does not cross, stated because it is the first thing a
reviewer will try.** A skill cannot be added to an already-installed
`agent.lgx`. `registerSkill` takes a `std::shared_ptr<ISkill>`, and there is no
wire format for a C++ object; Logos Core reaches a core module over Qt Remote
Objects in a separate process, so the remoteable surface is
`configure` / `start` / `stop` / `skills` / `status` / `invoke` and registration
is not on it. "Without modifying the core agent module" is therefore satisfied
in the sense the criterion states — no file the module ships is edited — and a
skill is added by a host that **links** the module.
`./examples/agent-console/run.sh` is such a host, and is the demonstration: it
compiles `notary.digest` from outside `module/src` against that one header,
`dlopen`s it, registers it through the module's public `registerSkill`, checks
the registry grew by exactly one, checks the answer against `shasum -a 256` of
the same input with a control on altered input, and requires
`git status --porcelain module/` to come back clean.

Long form: [`docs/skills.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/skills.md)
— the contract and its guarantees, the loader convention, the worked example
with its recorded output, a per-skill reference giving every parameter, an
honest table of which skills are wired to a running node and which are only
compiled, and the pluggable-inference seam.

### Spending threshold mechanism

[Approach](#approach) makes the argument for why the limit is an account rather
than an `if`. This is the mechanism.

**What the owner fixes.** Three numbers: `per_tx`, the largest single transfer
the agent may make unattended; `per_period`, the largest total it may move
within one window; and `period_blocks`, that window's length. Both limits are
needed — a per-transaction limit alone is drained by repetition, and a
per-period limit alone permits one catastrophic transfer.

**Where they live.** In the data of the agent's one policy account, at
`PDA(program, ["agent-policy/v1", agent_id])`, as 97 bytes:

```
version(1) || owner(32) || per_tx(16) || per_period(16) || period_blocks(8)
           || window_start(8) || spent(16)
```

little-endian throughout (`PolicyRecord`, `crates/agent-policy-core/src/lib.rs`).
LEZ rule 6 (`UnauthorizedDataModification`) refuses a data write to an account
from any program but its owner, and this program is the owner — so the ceiling
cannot be edited by the agent and the running total cannot be forged by anyone.
A record that is not 97 bytes, or whose version byte is not 1, decodes to an
**error** rather than to a policy: the difference between "no ceiling" and
"refuse". The three record layouts in that crate carry three distinct version
bytes so none can be read as another.

**The decision.** `SpendPolicy::authorize` is the whole of it, and it returns
either the ledger to write back or one of five typed refusals, each mapped to a
stable error code an integration may branch on:

| Refusal | Code | Meaning |
|---|---|---|
| `OverPerTx` | 6005 | over the per-transaction limit — "use `spend_approved`" |
| `OverPerPeriod` | 6006 | would carry the period total past the anchored limit |
| `WindowMisaligned` | 6014 | the period named is not a multiple of `period_blocks` |
| `WindowRegressed` | 6015 | the period named is older than the one the ledger holds |
| `PeriodZero` | 6017 | the policy has no period to account against |

The addition is saturating, so a hostile total near the top of the `u128` range
cannot wrap into "plenty left".

**The period, and the clock this chain does not have.** No program on LEZ can
read the block height — `ProgramInput` carries the program id, the caller, the
pre-states and the instruction, and nothing else. So the *caller* names its
period and the guest makes the naming binding, three ways at once: the window
must start on a multiple of `period_blocks` (6014), it may not be older than the
one the ledger records (6015), and the transaction is pinned to
`[window_start, window_start + period_blocks)` through `ProgramOutput`'s block
validity window, which the state machine rejects outside of with
`OutOfValidityWindow`. Sliding the window forward a block at a time, replaying a
closed period and jumping ahead to a fresh one are each refused by a different
one of those three. What it is not is a wall-clock period; it is a block-height
window and claims nothing more.

**Above the threshold.** `approve_spend` creates a marker account whose address
is derived from the payment itself:

```
spend_ref = SHA256("/lp-0008/v0.2/SpendRef/"     ‖ agent ‖ recipient ‖ amount ‖ nonce)
marker    = SHA256("/lp-0008/v0.2/ApprovalMark/" ‖ spend_ref)
```

so changing the recipient, the amount or the nonce names an account that does
not exist, and the nonce is what stops one approval authorising the same
transfer forever. `#[account(init, …)]` gives single *issue*; `spend_approved`
stamps the record as it consumes it, which gives single *use* (6018); and the
owner names an `expiry_block`, written into the marker, which `spend_approved`
pins the transaction to as `[0, expiry_block)` — so an expired approval is not
something this program refuses, it is a transaction no block will include. A
zero expiry is refused at issue (6021), because an empty range cannot be pinned
and "no window" is the bearer instrument the field exists to prevent. Who the
owner *is* is not an argument either: `approve_spend` reads it out of the policy
account and compares it to the signer (6012), so a compromised agent signing its
own approvals is refused by the same account it would have had to overwrite.

**The way back.** `init` cannot be undone — LEZ rule 4 forbids changing an
account's program owner, so no `close` instruction can exist — which is why
recovery lives in the record rather than in the address. `update_policy`, signed
by the owner the record names, re-fixes both limits and the period in place,
carrying the running total through untouched: raising a ceiling is not
forgiveness for what was already spent under the old one. `per_tx = 0` is a
policy rather than a mistake, and it is the brake an owner puts a suspect agent
in.

**Three layers, and only one of them is authority.** The chain refuses an
over-envelope `spend` with 6005 and no transaction is ever built. The module's
`wallet.send` compares first against a cached `SpendEnvelope`, which saves
proving cost on a payment the chain would refuse — and treats **everything
unknown as outside**: an unreadable envelope or an unknown period total forces
the approval path rather than the autonomous one. And the owner channel opens a
*reliable* channel — not a bare topic, because a dropped approval request looks
exactly like a refusal — identified by
`/lp-0008/1/owner-channel/<owner>/<agent>`, re-sends the byte-identical request
every 15 s and after 120 s answers `ApprovalVerdict::Unreachable` — terminal,
never a fallback to acting alone
(`module/src/owner_channel.h`; both timings are settable at runtime through
`meta.configure`, and they are the only two keys that skill reports as
`effective`). A reply that agrees on anything less than every field of the
request is refused, and a reply carrying `per_tx`, `per_period`, `period_blocks`
or `policy` is refused outright: an approval names a payment, it cannot change a
limit.

**What is bounded.** An *approved* above-threshold spend is not submitted today,
because the owner who anchored a policy cannot sign a second program
transaction. That is written up under [Known limitations](#known-limitations)
below and it is not hidden anywhere in this document; the safety property — that
nothing above the threshold is executed without the owner — holds in every run
recorded here.

Long form: [`docs/security-model.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/security-model.md)
§§1–6, with the commands to read any agent's live record back off the chain, and
[`docs/use-cases.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/use-cases.md)
§3, which is the accepted-below / refused-above demonstration with its controls.

### Agent-to-agent coordination protocol

A2A **v0.3.0**, carried over Logos Messaging. A2A §3.2.4 permits additional
transport protocols as extensions, provided they use clear namespace
identifiers and are clearly documented and specified; this binding claims that
clause, and states the cost of doing so rather than glossing it. The rule it
cannot satisfy is §3.1 — "A2A communication MUST occur over HTTP(S)" — so **an
off-the-shelf HTTP A2A client cannot talk to a Logos agent.** What interoperates
is the **data** — the Agent Card, the JSON-RPC request objects, the task
states — and any client that implements the binding's transport rules.

**Namespace identifiers**, because A2A §3.2.4 requires clear ones:

| Namespace | Value |
|---|---|
| `preferredTransport` | `logos-messaging` |
| URL scheme | `logos-messaging://<agent's shielded LEZ account>` |
| Card extension block | `x-logos` |
| Skill parameter-schema extension | `x-logos-parameters` |
| Content-topic application | `lp-0008` |

`preferredTransport` is a free `string` in the v0.3.0 schema and neither
`AgentCard` nor `AgentSkill` sets `additionalProperties: false`, so all of the
above are schema-valid extension members rather than junk smuggled through. No
method name is invented: the binding carries A2A's own `message/send` and
`tasks/cancel` and nothing else.

**Addressing.** Three content topics, on the LIP-23 grammar
`/<application>/<version>/<name>/<encoding>`:

```
/lp-0008/1/owner-<account>/json                one-to-one traffic, and the owner channel
/lp-0008/1/discovery-<namespace>/json          Agent Card publication
/lp-0008/1/task-<agentAccount>-<taskId>/json   one A2A task
```

A task topic is derived from the peer's account and the task id, and both ends
compute it the same way, so there is no rendezvous and no session setup: the
client publishes its request there, the server publishes its status updates
there, and the client reads them back off it.

**The card.** A2A's required set, plus an `x-logos` block carrying the two
things A2A has no slot for — who to pay and how much: `lezAccount` (the shielded
identity), `paymentAccount` (a public account, checkable by anyone with
`getAccount`), `shieldedPaymentKeys` (an `npk`/`vpk` pair, so a payer can credit
the agent privately instead), `pricePerTask`, and
`settlement: "lez-chained-authenticated-transfer"`. `skills` is read from the
registry rather than written as a literal. Cards are **signed** as an RFC 7515
JWS with a detached payload over the compact, key-sorted card without its own
`signatures` member; `alg` is the unregistered `secp256k1-bip340`, on purpose,
because JOSE registers nothing for Schnorr and a registered name would be a
false one, and `kid` is the **payment account** — the very thing the reader is
being asked to trust. `agent.card` refuses to emit an unsigned card rather than
emitting one.

**Lifecycle.** A2A's `TaskState` enum verbatim and with no additions —
`submitted`, `working`, `input-required`, `auth-required`, `completed`,
`canceled`, `failed`, `rejected`, `unknown` — with an unrecognised state name
treated as a protocol error rather than as a reason to invent a state. A2A
v0.3.0 publishes no transition matrix, so the one enforced here is the binding's
own, it is stricter than anything A2A requires, and it lives in exactly one
function (`canTransition`): nothing enters `submitted` except `TaskStore::create`,
`working → working` is the one legal self-transition, `working → rejected` is
illegal because rejection answers the *request*, and nothing leaves a terminal
state.

**The order of operations is check, post, pay**, and it is deliberate. A peer's
card is validated, it must advertise the requested skill, and the price and
payee are taken **from the card** because that is the figure the peer published
and the only one it is bound to; `max_price` is checked long before anything is
signed; transport readiness is checked, and only then is the task created; the
request is published, and a publish failure moves the task to `failed` and pays
nothing; only then is the price paid. A payment is recorded against a task only
through `recordPayment`, which refuses an amount with no settlement transaction
hash — an amount with no hash would make an unsettled task look paid for the
rest of its life.

**The return path.** `agent.update` publishes a full `TaskStatusUpdateEvent`
with `final` derived from the state rather than asserted by the sender, and
carries `metadata["x-logos"]["from"]` naming the publisher. `agent.poll` applies
a frame only if it parses, carries `kind: "status-update"`, names this task and
this context, says who published it, and was published by the task's **peer**
rather than by this agent. That author rule is load-bearing, not decoration: a
Delivery node receives its own publications, so without it a single process
could drive its own task to `completed` and the transcript would read exactly
like two agents cooperating. What the rule buys is stated exactly — it is not
authentication, since nothing is signed, but it does mean one process cannot
satisfy an assertion about a peer by talking to itself.

**What this protocol does not do**, in its own words rather than by omission:
there is no response — a request is published and the skill returns, so nothing
is ever acknowledged and no A2A error code is produced or consumed; **nothing
dispatches** — no code in the module takes an inbound request, looks up the
skill it names, runs it and publishes the states work moves through, so a
serving agent is this module plus a host that decides, and `completed` is a
claim by that host; task traffic is unsigned, so `x-logos.from` is a string the
publisher chose and a stranger who writes the peer's account there can drive a
task you opened into `failed`; the binding requires task traffic to run over a
reliable channel and the module wires it to a bare relay topic, which is open
work named as such; `tasks/get` is not implemented; and `TaskPort::refund` is
unwired, because a refund has to be signed by the payee, whose key the payer
does not hold.

Long form: [`docs/a2a-binding.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/a2a-binding.md)
— the full transport mapping with every message on the wire, card signing and
verification, the payment binding, §7 on what it does not do, §8's conformance
table against A2A §11.1 item by item, and §9, an eleven-step checklist for
implementing the other end.

### Security model: what the agent can and cannot do without owner approval

**Without asking anybody, the agent can:**

- **Spend up to `per_tx`, to any address it likes.** There is no allowlist. The
  policy binds *how much*, never *to whom* — recipient binding exists only on
  the approved path, where the marker commits to the recipient.
- **Repeat that up to `per_period` in each window, and again in the next one.**
  The period ceiling is real, but it is a rate limit rather than a total: a
  patient attacker still drains the account over enough periods. What it buys is
  time, and time is what an owner watching the chain needs.
- **Discover peers, open A2A tasks and settle them**, unattended, inside that
  same envelope — which is what every settlement in this submission is.
- **Consume an approval the owner has already signed**, for the payment it
  names — once, and only before its expiry block.
- **Act as itself everywhere else**: upload and delete under its storage
  identity, message its owner and its peers as itself, and publish a signed
  Agent Card advertising whatever it likes.

**Without owner approval, the agent cannot:**

| Attempt | Refused by |
|---|---|
| Exceed the per-transaction limit | 6005, and the program names `spend_approved` rather than merely refusing |
| Exceed the per-period limit by splitting the payment up | 6006 — the running total is on chain and only this program may write it |
| Reset the period early to get a fresh budget | 6014 / 6015 / `OutOfValidityWindow`, one each for sliding, replaying and jumping ahead |
| Anchor itself a second, looser ceiling | `init` on both accounts, and `create_policy` refuses any signer that is not the id the claim names (6020) |
| Re-fix the limits it was given | 6012 — `update_policy` compares its signer against the owner the record names |
| Raise the limits by presenting different numbers | there are no limits in `spend` at all; they are read out of the account |
| Borrow another agent's policy account | `PdaMismatch` — the address is derived from the account that pays |
| Forge an owner approval, or sign its own | 6007 / 6012 |
| Redirect an approved payment, replay one, or redeem an expired one | 6011 / 6018 / `OutOfValidityWindow` |
| Spend from the owner's account, or another agent's | the payer is whichever account signs |

**And a party who is not the agent can do nothing at all.** Knowing an agent's
id — which is public by design, because it is the address other agents pay it
at — no longer lets a stranger anchor a policy over it, brick it with
`per_tx = 0`, or take the address the honest owner needs. Both accounts require
a signature only the agent's holder can produce, and the second additionally
requires one only the agent's chosen owner can produce.

**What this does NOT protect against, stated at the same volume.** An account
holder can always call the program that owns its balance. The agent's LEZ is
held by LEZ's authenticated transfer program — measured, not assumed:
`getAccount` on a funded agent reports
`"program_owner":"J8otq1J8Zpjhhpp6FPfhFtWKTCkLjthdk12cwHiMZCTB"` — and that
program's `transfer` asserts only that the sender is authorized. **So whoever
holds an agent's key can move that agent's balance by calling the transfer
program directly, with the policy program nowhere in the transaction.** Nothing
here prevents that and nothing here claims to. It also cannot be fixed inside
this program: LEZ rule 5 lets a program debit only accounts *it* owns, so gating
a balance requires the balance to live in an account the policy program owns —
which changes how funding works and what `getAccount` shows. That is a different
design, not a patch.

The honest guarantee is therefore in two parts, and only the second is
unconditional:

- **a compromised agent cannot use the policy path to exceed its policy** —
  every row of the table above is scoped to that path;
- **a party who is not the agent cannot touch the policy at all** — and this
  half is not scoped, because a stranger has no other path either.

The residual the two-signature anchor closes is griefing and impersonation
rather than theft from a key-holder, and it is worth being exact about that
rather than claiming more.

**Three things here look like controls and are not.** The module's envelope
check is a courtesy — it saves proving cost on a payment the chain would refuse
and stops nobody who has replaced the process. The owner channel's timeout is a
property of an honest agent — an attacker simply does not send the request. And
the inference layer is advisory by construction: it can only ever move an answer
toward *decline*, the amount paid is always the offer's price and never a number
read out of a model's reply, so a backend that obeys an injected "authorise
10000" cannot turn that into a transfer. The pattern is the same in all three:
anything the agent process decides, whoever holds the agent process decides
differently. Only the chain survives that.

**Assumptions.** The sequencer enforces its own state machine (rule 4, no
program-owner change; rule 5, no debiting an account you do not own; rule 6, no
data write from any program but the owner; rule 8, balance preserved across a
transaction). The privacy circuit is what the sequencer pins. The owner's key is
not on the agent's machine — if it is, the two signatures collapse into one. And
the agent's key is not stolen before it claims an owner; an attacker who takes
it first designates itself, but such an attacker already holds the balance
directly, so that residual costs nothing that was not already lost.

**Checked by execution, not by reading.** `crates/agent-verifier-adversarial`
runs each hostile call above against the **deployed** binary under the same
risc0 executor the sequencer runs, and asserts the code it halts at — each
paired with the honest call it differs from in one field, because a table that
only ever refuses says nothing about what is accepted. One trap for anyone
integrating: the codes declared in the guest reach a caller **offset by 6000**,
since `SpelError::error_code` returns `6000 + code` for a custom error, so the
log reads `Program error [12005]: Program error 6005: …`; and refusals from the
macro's own account validation — `AccountAlreadyInitialized`, `PdaMismatch` —
carry no numeric code at all and are matched by name.

Long form: [`docs/security-model.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/security-model.md),
whose §8 is the whole executed table.

### Known limitations

Every entry below is **open** except the two retractions at the end, which are
closed and are kept because the false claim was ours.
[`docs/limitations.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/limitations.md)
is the full list, and it is the document to read first.

**The owner cannot approve a spend after anchoring a policy.** The most serious
open defect here, and it is in the tooling rather than in the program. `spel`
builds every transaction against nonce 0 while the sequencer checks the nonce
for exact equality, so a public signer that still carries the default program
owner gets exactly **one** program transaction: a second is built stale,
submitted, given a hash, and silently dropped. `approve_spend` requires the
owner as signer and compares that signer against the `owner` field of the policy
record on chain, so the approval must come from the account that anchored the
policy — which has already spent its one transaction on `create_policy`.
`update_policy` inherits the identical constraint. That removes half of the
spending-threshold design, and the module does not pretend otherwise: an
approved above-threshold spend returns
`{"outcome":"approved","submitted":false}` and names `spend_approved` as the
path that would carry it. Two ways out, neither yet tried: make the owner
account program-owned before anchoring — a funded account is exempt, and
`DumJ4LCB…` holds two landed anchors as the worked example — or stop committing
the signer's identity, so an approval can come from a different account than the
anchor.

**The policy bounds the policy path, not the agent's balance.** Open by design,
not closable inside this program, and set out in full under
[Security model](#security-model-what-the-agent-can-and-cannot-do-without-owner-approval)
above.

**Nothing dispatches.** The module reads inbound A2A requests and publishes
status updates, but nothing in it routes a request to the skill it names, runs
it, and publishes the states that work moves through. A serving agent here is
this module plus a host that calls `messaging.receive`, decides, and calls
`agent.update` — so a `completed` is a claim by that host about work it says it
did.

**No model has ever been run against the inference port.** `StubLocalBackend` is
a rule table with an honest name — no weights, no tokenizer, no inference of any
kind. `OpenAiCompatibleBackend` builds a real chat-completions request and
parses a real reply, but the only transport it has ever been given is a fake and
**no request has left this repository**. The decision is not even in the demo
path: `scripts/a2a-task.sh` still decides a task price with a shell `if`. What
the work demonstrates is the seam and its failure behaviour, which is worth
something and is not "an agent driven by a model".

**The storage skills now run against a live node, and the ports they run on
are still the host's.** `./scripts/skills-live.sh` opens a real Logos Storage
node and calls `storage.upload`, `download`, `list` and `share` through the
module's own `invoke()` — not through the C driver, which proves the library and
not the skills. The digest is recomputed by the shell outside the driver, the
same comparison is shown to refuse altered bytes, and an address the node says
it does not hold is refused by both `download` and `share` with nothing written
and nothing published. What that does not close: nothing in `module/src` opens a
Storage node, so a module *loaded* by Basecamp still refuses every `storage.*`
call until a host supplies the port.

**`messaging.create_group` works through a host's port and not through the
module's own**, which is a defect measured rather than inferred: the module
passes the group id where a Logos content topic belongs, and a real node
subscribes to that topic before opening the channel. On one node, two calls
apart, the bare id is refused and a documented content topic is accepted.

**A settlement takes minutes, not milliseconds.** The privacy-preserving path is
bounded by the prover rather than by execution, and a proof blocks the paying
module for as long as it takes — 432 s in the recorded run. That is the honest
figure for an agent that pays.

**Anchors die with every guest change, and the guest is effectively frozen.**
Both of an agent's accounts are PDAs of the program id, so rebuilding the guest
orphans every claim and every anchor made under the old one — and "rebuilding"
includes editing a comment, because `#[lez_program]` generates a `panic!` and a
Rust panic bakes `core::panic::Location` into the binary. Add a line above it and
the ImageID moves. Re-anchoring costs two transactions per agent and a fresh
signer for each.

**An approval cannot be revoked before its expiry.** `approve_spend` is `init`,
so a marker cannot be re-issued to cancel it. Shortening the horizon is the only
control there is, and it is the owner's to choose.

**Only half of a settlement is publicly readable.** `getAccount` reads the
public state only and answers with a fully-populated default account for a
shielded address exactly as it does for one that never existed, so it is not
even an existence check. With a public payee the credit side is checkable by
anyone and the debit side is not; with a shielded payee neither is, and only the
payee can confirm the amount with its own viewing key. The debit is still
constrained by rule 8, which requires total balance to be preserved across a
transaction.

**A2A conformance gaps**, beyond the HTTP one already stated: no response path
and therefore no A2A error codes; `tasks/get` unimplemented; task traffic on a
bare relay topic where the binding requires a reliable channel; refunds unwired.
A2A v1.0 additionally breaks three things written here — state names, `kind`
discriminators, and RFC 8785 card canonicalisation — and is deliberately not
targeted.

**The owner's second app does not hold a key.** It is bound to the owner's
*account* and does not sign its reply; sender ids on that channel are
self-declared. What is demonstrated over Logos Messaging is reach, correlation
and real time — not key custody. The authority over an above-threshold spend is
the approval account on chain, which only the owner's signature on
`approve_spend` can create.

**Two commands, not one.** Deploying and configuring the published agent in
Logos Core headless is one command; standing up an agent of your own is a second
and needs faucet-funded testnet balance no script can supply. A wrapper over
both is writable and deliberately unwritten, because it would report one exit
code for two unrelated failures.

**Both `.lgx` packages are installed by hand**, because Basecamp 0.2.2's Package
Manager installs from a configured repository only. That is a property of the
host rather than of the packages, and it is as true for a reviewer as for us.

**Delivery has no Linux library to link against.** Upstream publishes no
`liblogosdelivery.so` and never has, so both Linux plugin variants carry the
delivery code path with no library beside them and
`meta.configure("delivery","on")` there reports the file it could not open
rather than starting a node.

**The video demo, the last criterion to close, is one file rather than two.**
It was published as two films first: three of the prize's illustrative use cases
between them and one in the half a reviewer would most likely open. The
criterion says *a recorded video demo*, singular, so the pair satisfied it only
for someone who watched both. The checklist below records what it now runs and
how that is checked.

**Two limitations this project claimed and that did not survive being checked**
are recorded as retractions rather than quietly dropped: that a shielded agent
could not be paid at its shielded account — which was a missing `PrivateForeign`
variant in the `spel` this repository vendors and builds, closed by settlement
`5942d6cd…` in block 9360 — and that a loaded module could not have a Delivery
node, which confused "a host cannot pass a `std::function` across the plugin
boundary" with "a module cannot build one".

### Integration instructions

**First, check the claims rather than the document.** From a clean clone, with
no keys, no funded account and no local sequencer — only a Rust toolchain:

```console
$ ./scripts/demo.sh                      # the program on chain is the binary here
$ ./scripts/verify-deployment.sh         # every anchor and settlement, re-read
$ ./scripts/check-docs.py                # every path, link and citation resolves
```

**Run the published agent in Logos Core, headless — one command.**

```console
$ ./scripts/logos-core-headless.sh storage
```

It installs `module/agent.lgx` into the user modules directory the way
Basecamp's own installer does, picking the variant for the machine, then runs
load → `configure()` → `start()` with no GUI, no window and no display, binding
the agent to the owner and policy account recorded in `artifacts/agents.tsv` and
reading both back out of `meta.status`. That manifest is committed, so a fresh
clone needs no chain access for this. What it needs, and there is no compiler
among it — the harness ships pre-built per variant under `module/harness/`:

1. **A Logos Core runtime.** On Linux, `./scripts/fetch-logos-core.sh` unpacks
   the published AppImage in one checksum-pinned command with no installer, no
   root, no FUSE and no display. On macOS, install LogosBasecamp from the
   `.dmg`, because upstream publishes no headless build there.
2. **A glibc and libstdc++ new enough for that runtime** — a floor upstream sets
   and this repository stays below on every axis.

`./scripts/harness-no-toolchain.sh` runs the whole thing inside a stock
`ubuntu:24.04` container and refuses to report anything if it finds a compiler,
a Qt SDK, a `logos-cpp-sdk` checkout or `nlohmann/json` there.

**Stand up agents of your own — a second command.**

```console
$ SIGNER=<funded public account id> ./scripts/deploy-agents.sh
```

It creates each agent's shielded identity, funds it, opens its public receiving
account, and anchors its envelope in the two signatures the program requires. It
names whichever prerequisite is missing rather than failing inside a
transaction, and there are five: a `wallet` binary built from LEZ at the pinned
revision (a wallet home is not portable between builds); a `spel` built from
`vendor/spel`; a wallet home at `LEE_WALLET_HOME_DIR` holding `SIGNER`'s key;
testnet balance on `SIGNER` for the three funding floors, which needs a faucet
and is the one thing no script can supply; and network reach to
`SEQUENCER_URL`. It is deliberately **not** idempotent — a second run derives
the same two addresses and `init` refuses both, which is the single-use
guarantee working, and the script reports it as already-anchored from
`artifacts/anchored.tsv`.

**Install it in the Logos app.** Unpack `module/agent.lgx` (`type: core`) into
the user modules directory and `app/agent-ui.lgx` (`type: ui`) into the user
plugins directory, by hand, per `docs/basecamp.md` and `app/README.md`. Both
carry `darwin-arm64`, `linux-amd64` and `linux-arm64`.

**Drive it.** Everything the module offers is reached through
`invoke(name, paramsJson)`:

| Call | What it gives you |
|---|---|
| `meta.skills` | every registered skill and its parameter schema |
| `meta.status` | what the module is bound to, its `durability` block, its channel counters |
| `meta.configure` | `delivery`, the two approval timings, the three delegate commands, and the local mirrors of what is anchored on chain |
| `agent.card` / `agent.discover` | this agent's signed card; other agents' cards off a discovery topic |
| `agent.task` / `agent.poll` / `agent.update` | open a task and pay for it; read a peer's updates; publish your own |
| `wallet.send` / `wallet.balance` | a spend through the anchored policy; a balance read from the sequencer |

**The three delegate commands are the integration seam that matters most.** A
plugin Basecamp loads has no crypto library, no wallet and no HTTP client, and a
host cannot hand it a closure — so `card_signer`, `pay_signer` and
`policy_source` are each a *command* the module runs, handing it input on stdin
and checking the single line it prints before believing any of it: base64url for
a signature, 64 lower-case hex for a settlement, decimal digits for each limit.
The first is `scripts/sign-agent-card.py` with `--sign-input`; the other two are
`scripts/agent-spend.py` with `--settle` and with `--envelope`. `policy_source`
is what makes
`agent.task` able to pay unattended — it reads the agent's own **anchored**
policy account off the chain on every priced task, and anything it cannot read
is *unknown*, which is outside the envelope, so the payment is held for the
owner rather than made.

**Add a skill.** Implement `logos::agent::ISkill` against
`module/src/agent_module_interface.h` — that one header, nothing else — and call
`registerSkill` from a host that links the module.
`./examples/agent-console/run.sh` is a complete worked example that compiles,
loads and checks one. A skill shipped as a separate binary exports
`logos_agent_skill_abi_version` and `logos_agent_skill_create`.

**Write the other end of the A2A protocol.**
[`docs/a2a-binding.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/a2a-binding.md)
§9 is an eleven-step checklist in the order the work has to happen — run a
Delivery node and wait for `nodeStarted` rather than for `start` to return, get
a LEZ account, build and sign a card, publish and republish it, subscribe to
your own task topics, accept requests, publish status updates carrying
`metadata["x-logos"]["from"]`, expect payment after submission, handle
cancellation, and persist your task store.

**Branch on refusals, not on strings.** The program's error codes are
deterministic and stable, the retired ones (6001, 6004, 6013) are left unused
rather than recycled, and they reach a caller offset by 6000.

Long form:
[`docs/DEPLOYMENT.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/DEPLOYMENT.md)
for what is live and how to re-verify it,
[`docs/basecamp.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/basecamp.md)
for building, packaging and installing into the Logos app,
[`docs/use-cases.md`](https://github.com/edenbd1/lp-0008-autonomous-agent-module/blob/main/docs/use-cases.md)
for running the illustrative use cases, and `README.md` for the end-to-end

- [x] **MET — Two or more agents can discover each other via Agent Cards, execute
  a task following the A2A lifecycle, and transfer LEZ payment autonomously,
  without owner intervention.**
  A conjunction of three, and **one invocation does all three**:
  `./scripts/delivery-in-plugin.sh settle`. Two modules loaded through
  `QPluginLoader`, each with its own Delivery node, its own LEZ account, its own
  wallet and its own working directory, on one public topic. The buyer is handed
  no price and no payee — it reads both off the seller's signed card, which
  arrived over the public network seconds earlier — checks the price against the
  envelope its owner anchored **on chain**, sends the A2A request, and settles:
  **`ed8c3514…374b8cb3`, block 9477**, on chain and checkable now. Then each
  agent's own `TaskStore` walks `submitted → working → completed` on status
  updates the **other** account published.
  The two-process shape is not decoration, and neither is the seller. A Delivery
  node receives its own published messages, so a single process could satisfy any
  "a card arrived" assertion with every other agent on earth switched off; each
  side here accepts only a card naming the **other** account. The seller runs the
  identical code path against a card advertising no price and comes back with no
  settlement hash — without that control, "the module reported a transaction hash"
  would be indistinguishable from "the module reports one whenever it opens a
  task". And before each side polls, it publishes a `completed` update *for its
  own task*, as itself, onto the very topic it is about to read; the assertion is
  not "no such update was applied" (which would also hold if the frame never
  arrived) but that the poll **counted** one and ignored it. That assertion was
  watched failing against a build with the author rule replaced by `if (false)`.
  **Three things this does not claim.** *Nothing dispatches*: `messaging.receive`
  reads an inbound request and `agent.update`/`agent.poll` are the return path,
  but nothing in the module takes that request, looks up the skill it names, runs
  it, and publishes the states that work moves through — a serving agent here is
  this module plus a host that calls `messaging.receive`, decides, and calls
  `agent.update`. So `completed` is a claim by the server's host about work it
  says it did. No *owner* is in either path, which is what the criterion asks
  about, but "autonomous" here means unattended, not model-driven. *A status
  update is not authenticated*: `x-logos.from` is a string the publisher chose;
  cards are signed and task traffic is not. *The server keeps no record of what it
  serves*: ordering on the serving side is the host's discipline.
  `docs/a2a-binding.md` §7 is the long form. `TaskPort::refund` is also unwired —
  a refund would have to be signed by the payee, whose key the payer does not
  hold.

### Usability

- [x] **MET — Provide a documented skill interface (module/SDK) that can be used
  to add new skills without modifying the core agent module.**
  `logos::agent::ISkill` — `name()`, `parameterSchema()`, `invoke(json)` — plus
  `registerSkill()`, specified in `docs/skills.md`. It is the only header a skill
  needs: not the plugin header, not the Logos SDK, not Qt, and not a JSON library.
  The interface is defensive by design because third-party code is the whole
  point: `name()` is called *before* the module takes its lock, so a skill that
  calls back in cannot deadlock a non-recursive mutex; a throwing `name()` is
  caught and reported rather than escaping into the host; a duplicate name is
  **refused rather than overwritten**, so one plugin cannot shadow another's
  `wallet.send`; and `invoke()` drops the lock before dispatching and rejects a
  non-JSON return.
  Demonstrated end to end by `./examples/agent-console/run.sh`, which compiles a
  skill living outside `module/src` against the interface header alone, `dlopen`s
  it into the module, checks the registry grows by exactly one, and checks the
  answer against something that is **not** this repository — the digest must match
  `shasum -a 256` of the same input and must not match the digest of altered
  input, which is what stops a registered-but-never-run skill passing. It also
  runs `git status` over `module/` and requires it clean: the criterion's words,
  checked. This is a CI step ("A third party adds a skill without editing the
  module"), which it was not — it broke for one commit when a new module source
  file was added to the build everywhere except this example's link list, under a
  comment saying the two lists must stay identical, and nothing noticed.

## FURPS Self-Assessment

### Functionality

The agent holds a shielded LEZ account, signs its own transactions, and spends
under a ceiling the chain keeps in state only its own program may write. It can
also be **paid** at that account — by keys its signed Agent Card publishes rather
than by an id — so a settlement can hide both ends rather than only the payer's.
All twenty-one default skills are implemented and registered, and the registry is
asserted against the loaded binary rather than against the source, because this
repository has shipped skills that were implemented, documented and unreachable.

The A2A coordination path used to have to be described in parts, because it ran
in parts: cards and discovery on the network, settlement from a shell script, and
a lifecycle driven locally. Those are now one call. Two loaded modules discover
each other's signed cards on a Logos Messaging topic; the buyer reads the price
and the payee off the card that arrived — it is handed neither — checks them
against the envelope its owner anchored on chain, sends the A2A request, settles
on the public testnet with no owner key in the path, and both stores then walk to
`completed` on frames the *other* account published.

**The limits are not incidental.** The **owner cannot approve an above-threshold
spend** after anchoring a policy, because LEZ permits one program transaction per
public signer and the anchoring owner has spent it on `create_policy`; that
removes half of the spending-threshold design and is the most serious open defect
here. **Nothing dispatches**: the module reads inbound requests and publishes
status updates, but nothing in it routes a request to the skill it names, runs it
and publishes the states that work moves through, so the serving side is this
module plus a host that decides. **Storage skills have never touched a live node**
from inside the module — the file-vault use case drives a real Logos Storage node
through a purpose-built C driver, which proves the node ABI and not the skill. And
**no model has ever been run against the inference port**: the local backend is a
rule table with an honest name, the OpenAI-compatible backend has never made a
request that left this repository, and the acceptance decision is not even in the
demo path. What the inference work demonstrates is the seam and its failure
behaviour, which is worth something, but it is not "an agent driven by a model".

### Usability

Two audiences. A **skill author** gets a three-method interface, one header, a
registration call that refuses to let one plugin shadow another's `wallet.send`,
and a spec — this is the strongest usability story here, and it is demonstrated
by compiling a skill outside the module tree and checking the module's answer
against `shasum`. An **owner** gets a CLI that deploys and anchors three agents
reproducibly, a `.lgx` that genuinely loads in Basecamp on all three published
platforms, a second `.lgx` that gives it a **window** in the Logos app, and a
Logos Core **headless** command that installs, loads, configures and starts the
module with no GUI, no display and — since the harness ships built — no compiler.

What the owner still does not get is a single command that does *both* halves.
Deploying the published agent in Logos Core is one; standing up an agent of your
own is a second, and it needs testnet balance no script can conjure. The wrapper
over the two is deliberately unwritten, because it would return one exit code for
two unrelated failures. Both `.lgx` packages must also be installed by hand,
because Basecamp 0.2.2's Package Manager installs from a configured repository
only; that is as true for a reviewer as for us, and the commands are in
`docs/basecamp.md`.

### Reliability

The design is fail-closed in the places where failing open would move money: an
unreachable owner is terminal rather than permission to act alone; an approval
that names different terms is refused; a limit that will not parse becomes zero,
which holds every spend and declines every offer; an unreachable inference backend
declines; and `scripts/a2a-task.sh` refuses to write its own manifest unless the
recipient's balance moved by exactly the price — a rule added because an earlier
version produced confirmed on-chain proofs that a policy permitted 25 LEZ and
moved nothing at all. Skill dispatch is exception-isolated and lock-free at the
call site.

Restart recovery is demonstrated rather than designed for, and the demonstration
is falsifiable: a truncated snapshot **refuses** the start rather than coming up
empty, because a corrupt file loading as an empty task list is how a paid task
gets paid twice, and CI puts the module back in the state where it constructs no
snapshot and requires the suite to go red.

Against that, the honest counterweight: assertion counts are not the measure, and
this repository has twice shipped assertions that could not fail. That is why
every load-bearing check here has a negative control beside it that was watched
failing — the Agent Card mutations, the swapped package binary, the swapped
harness binary, the deleted author rule, the deleted snapshot construction, the
companion module rebuilt against the wrong Qt. A recent sweep of the workflow and
the scripts it runs went looking for the remaining ones and found a tamper control
whose mutation could equal the value it mutated; it derives the mutation now.
Where a control could not be exercised live it is said so: this transport hands a
node its own relay messages but not its own reliable-channel frames, so the rule
refusing a self-authored *request* is exercised in a unit test against a frame
written for the purpose, with the falsifying pair beside it.

### Performance

No LEZ execution meter exists to measure on v0.2.4, so the benchmark document
measures the budgets that do exist rather than inventing a CU number: 0.83% of one
public-execution cycle budget for a full autonomous settlement, one chained call
of the ten permitted, and a settlement size read back from the sequencer rather
than estimated. Cycle counts come from executing the deployed binary under the
same executor the sequencer runs. Account count dominates the cycle cost — each
declared account is deserialised in and re-serialised into the journal out — and
the period ledger is free, costing one cycle for a branch.

The real bottleneck is **proving time**, not execution. The settlements take the
privacy-preserving path, which is bounded by the prover rather than by the 32M
public-execution cap. A proof blocks the paying module for as long as it takes —
432 s in the run recorded in `docs/basecamp.md`. That is the honest number for
an agent that pays: a task settlement is minutes, not milliseconds. The second
real operational cost is that **anchoring is one-shot per signer**, which is the
same constraint that makes the above-threshold approval path unreachable.

### Supportability

The `CI` workflow runs ten jobs and gates every push; two further workflows are
scheduled and on demand, because they cannot be fast — the end-to-end lifecycle
against a real standalone sequencer at `RISC0_DEV_MODE=0`, and the run that loads
this module alongside the wallet, storage and messaging modules. Neither has a
skip path. The CI file documents in comments exactly
which suites do **not** run there and why — Qt and an installed Basecamp for the
macOS load tests, a Nim and `librln` build for the node drives — because a suite
silently absent from CI is indistinguishable from one that was never written. A
badge is still not the check: run the `gh run list` command in the Supportability
checklist above, because green is a property of a tip that moves.

Three things make the codebase maintainable in a way that is checkable rather than
claimed. Documentation is gated: `./scripts/check-docs.py` resolves every path,
link, line citation and symbol citation in every document here, and cross-checks
every skill-count claim — and every harness's skill table — against what the
module actually registers, because this project has shipped documents citing files
that had been renamed and a test whose expectation the registry had outgrown.
Evidence is generated: `./scripts/submission-evidence.py` produces every on-chain
figure in the submission document and `--check` fails CI when the chain and the
document disagree, because a previous draft carried a hand-typed settlement table
whose balances had never been true and whose lead transactions the deployment
guide disowned by name. And debuggability is deliberate: every failure path
returns JSON naming the skill and the half that failed, and `share` takes both
ports specifically so it can report whether storage or delivery failed rather than
blaming the wrong one.
